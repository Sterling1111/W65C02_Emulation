# HD44780U controller and 16x2 display

The code identifies its controller as Hitachi HD44780U. The board connects
an A00-ROM, 16-column, two-row, 5x8-dot character module to the W65C22.

The reference is the manufacturer's **HD44780U (LCD-II), ADE-207-272(Z),
September 1999, Rev. 0.0**, available as a
[Hitachi datasheet mirrored by Adafruit](https://cdn-shop.adafruit.com/datasheets/HD44780.pdf).
Relevant sections are registers/memory (pp. 9–12), CGRAM (pp. 19–20),
interfaces/reset (pp. 22–23), instructions and timing (pp. 24–31), and bus
waveforms (pp. 58–59). This is the manufacturer's document, not a tutorial for
an unspecified compatible module.

## Corrections

- Writes latch on E's falling edge. RS and R/W select the transaction;
  reads drive the data bus only while E and R/W are high.
- Both eight-bit transfers and high-nibble-first four-bit transfers work.
  Four-bit status and data reads require two E pulses; only a complete data
  read advances memory. DB0–DB3 are not driven by the LCD in four-bit mode.
- Status reads return BF plus AC; data reads return DR and prefetch subsequent
  data. Address-set/cursor-shift commands prime DR. A read immediately after a
  write, without an address-set command, can return the previous DR value.
- Busy time comes from emulated time, replacing host TSC frequency guesses.
  Writes while busy are ignored. Status reads remain available while busy.
- Power-on initializes the controller to eight-bit, one-line, display-off,
  increment/no-shift mode and holds BF for 10 ms. At the nominal 270 kHz
  oscillator, clear/home use 1.52 ms and ordinary instructions/data operations
  use 37 microseconds. Commands 02 and 03 both select return-home.
- Data-transfer AC readback changes after BF clears. Figure 10 gives
  `tADD = 1.5/fOSC`; this is used instead of the table's rounded 4-microsecond
  annotation (5.556 microseconds at 270 kHz). Status reads do not change AC.
- DDRAM wraps correctly at 27↔40 and 67↔00 in two-line mode, and 4F↔00 in
  one-line mode. Pointer movement never forms a pointer before allocated RAM.
- CGRAM is 64 raw bytes. Eight 5x8 custom glyphs have the documented 00/08,
  01/09, …, 07/0F aliases. Bits 4–0 select left-to-right pixels; the upper
  three stored bits do not draw dots. Addressing wraps modulo 64 in either
  direction.
- Clear/home select DDRAM, reset AC and display shift. Clear preserves CGRAM,
  sets the increment bit, and retains the entry-mode shift bit. Home preserves
  DDRAM contents and entry mode.
- Entry-mode display shifting applies to DDRAM writes only. Reading DDRAM or
  accessing CGRAM advances AC without scrolling. Explicit display shifts do
  not change AC and wrap each 40-character line independently.
- Function-set N controls memory geometry independently of the physical panel
  size. The related four-row helper maps module rows into two controller lines
  and scrolls across the full 40-character lines.
- Display-off blanks every physical dot while retaining memory. Previously the
  pixel loop repeatedly blanked one column and left other columns stale.
- Cursor underline and block blink obey D/C/B. Blink uses 102400 oscillator
  periods per half-cycle (about 379.26 ms at 270 kHz), independently of host
  CPU usage or frame rate. Rendering does not advance controller time.
- Pixel lookups reject invalid x/y coordinates rather than accidentally reading
  a neighboring row. Character-cell gaps remain distinct from inactive dots.

## Integration and API

`LCD` owns the electrical bus transaction state and timing. The existing
`vrEmuLcd` character core retains its MIT attribution and supplies memory,
command behavior, font lookup, and rasterization. Its direct full-byte helpers
are untimed; board software reaches the timed `LCD` interface through the VIA.

Board wiring is PA7=E, PA6=R/W, PA5=RS and PB7..PB0=DB7..DB0. In four-bit
mode, only PB7..PB4 carry data. `PortBus` passes the VIA's output mask to the
LCD so turning PB into inputs releases the bus without rewriting LCD data.

- `LCD::portAWrite(byte)` sets control levels and detects E edges.
- `LCD::portBWrite(byte, outputMask)` sets host-driven data pins.
- `LCD::portBRead()` returns resolved digital bus levels.
- `LCD::dataOutputMask()` indicates the lines currently driven by the LCD.
- `LCD::isBusy()`, `readStatus()`, and `readAddress()` are inspection helpers.
- `LCD::advanceTime(nanoseconds)` advances standalone tests deterministically.
- `LCD::tick(cpuFrequencyHz)` advances one board clock period, retaining
  fractional nanoseconds. Its frequency argument must be finite and positive.
- `LCD::powerOn()` reapplies power-on initialization. The board reset key does
  not call it: an HD44780 module has no CPU reset connection.

`System` advances both LCD time and VIA PHI2 on every emulated clock cycle,
including CPU wait/stop cycles. CPU MHz changes affect elapsed time per cycle;
the LCD's own oscillator frequency remains independent. A constructor argument
can select a different LCD oscillator for timing tests.

The SFML window takes a pixel snapshot under the CPU mutex and draws it in one
vertex batch. It no longer invents pre-reset character blocks or applies
frame-dependent brightness transitions. The panel is mounted on the full [breadboard view](Breadboard-view.md)
and drawn as a green PCB with plated mounting holes, a black metal
bezel, and dark blue glass, matching the reference hardware. Static shading
is cached in a render texture; pale blue-white dots use the controller pixel
snapshot. These materials are presentation choices, not a simulation of
liquid-crystal optics.

The standard Hello World ROM now issues function-set before clear. The older
unrolled example now initializes the stack, polls BF for every transfer, and
clears/homes the display on reset. It no longer depends on artificially slow
instruction execution to satisfy LCD timing.

## Scope and timing conventions

The verified target is the board's **16x2, 5x8-dot character module**, including
one-line controller addressing and four/eight-bit interfaces. The F bit is
retained, but 5x10 glass/ROM rasterization and the library's unrelated graphics
LCD path are not modeled/validated as part of this module. The existing A00
font table is retained; it is not a newly reconstructed mask ROM.

Commands update logical memory/display state atomically when accepted. BF and
AC readback use the datasheet timing; individual internal oscillator phases,
analog LCD voltages, contrast, persistence, and nanosecond pin setup/hold
violations are not simulated. Power-on assumes the datasheet's valid 5 V supply
ramp. Undefined CGRAM starts at zero for reproducibility. Invalid DDRAM holes
have deterministic backing storage but are not promised hardware behavior.

Four-bit software must finish both halves of each transfer. An RS/RW change
mid-pair discards the incomplete pair. Invalid host/LCD bus contention is
resolved in favor of the explicit host drive. The model keeps undriven data
levels for digital bus holding; it does not model pull-up RC behavior. Do not
infer electrical conformance from these fallback behaviors.

## Validation

`SystemTest/LCDTests.cpp` checks power-on and instruction timing, E-edge
semantics, eight/four-bit status/data transfers, initialization recovery, DR
prefetch, DDRAM/CGRAM wrapping, custom-glyph aliases and orientation, scrolling,
display blanking, cursor/blink, pixel bounds, and CPU/VIA integration. The same
tests run with address and undefined-behavior sanitizers. ROM smoke checks and
a capture of the real SFML window verify the assembled program and rendering.
